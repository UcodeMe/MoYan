# fe-self-check：三维交付自检

对本次交付（阶段 3 产出的全部变更文件）执行三个维度的自检。自检对象是**本次变更**，不是全工程；但变更影响到的既有交互链路也要覆盖。

## 0. 输入

- 上游产物：proposal.md、specs/**/spec.md（Requirement/Scenario）、design.md、tasks.md（或《本次开发说明》dev-notes）
- 本次变更文件清单（阶段 3 记录）
- `openspec/.project-frontend/theme-palette.md`（颜色基线）
- 参考实现文件（续接路径取 design 指向的目标/相邻代码；现场开发路径可取阶段 2 命中的场景）

## 1. 维度一：功能点切片

**先建切片清单，再逐片对账。**

1. 构建功能点切片清单：以 specs 的每个 Requirement/Scenario 为主（change 下的 spec 为增量格式：ADDED 全量核对、MODIFIED 核对改动后的行为、REMOVED 确认未再实现），结合 tasks.md 条目与 proposal 的范围内清单，拆成不可再分的功能点（一个切片 = 一条可独立验证的行为）
2. 逐片映射：切片 → 实现位置（文件+关键代码段）→ 状态判定：

| 状态 | 含义 |
|------|------|
| ✅ 已实现 | 有对应实现且逻辑完整 |
| ⚠️ 部分实现 | 有实现但缺分支/缺字段/缺状态 |
| ❌ 缺失 | 无对应实现 |
| ➕ 超范围 | 代码实现了需求外的功能（须说明理由或移除） |

3. 核对 tasks.md 勾选状态与实际一致（勾了没做、做了没勾都算 issue）

## 2. 维度二：交互逻辑

1. 列出本次交付的全部交互事件（点击/输入/选择/提交/跳转/弹窗开合/异步请求）
2. 每个事件按五环检查：**触发 → 即时反馈 → 结果呈现 → 异常路径 → 边界情形**
   - 即时反馈：loading/禁用态/按钮防重复提交
   - 异常路径：请求失败提示、校验失败提示且中止提交（Touch UI：`$.validate.verifyAll` 为 false 必须 return）
   - 边界情形：空数据空态、超长文本、必填缺省、重复操作、返回/取消路径
3. 与 specs 的 Scenario（GIVEN/WHEN/THEN）逐条对照：每个 Scenario 在交互层能否走通
4. Touch UI 专项（按 design、package 依赖、本次变更文件的 import/模板语法/CSS 类名判断实际使用的库；只检本次前端切片真实涉及的库，禁止为了判断组件库读取 index）：
   - touchui2（JWC 形态）：`Wade.setRatio()`/`Wade.JWC.init(true)` 是否就位、`@Part` 局部刷新 id 与 `$.ajax.submit` partids 一致、事件用 `tap` 不用 `click`、手机端响应规则类（`-phone-`）是否配置
   - touchvue2（Vue2 形态）：`.vue` 内不得出现 `jwcid` JWC 模板属性、循环/条件用 `v-for`/`v-if` 而非 `@Foreach`/`@Conditional`、Touch UI 组件 DOM 骨架（`c_form`/`c_table` 的 ul/li/label/value 层级）在单文件组件内保持完整未被拆散、复用工程既有请求/校验封装不并行造第二套

## 3. 维度三：颜色配色

以 theme-palette.md 为唯一基线：

1. **硬编码检查**：grep 本次变更文件中的 `#hex / rgb(` 色值，逐个判定：属于令牌色（应改为引用令牌/皮肤类）、新颜色（须问询是否入令牌表）、违规散落色（改掉）
2. **令牌一致性**：主操作/次操作/危险操作按钮用色符合组件映射（如主按钮 `e_button-blue` 或工程实际皮肤类）；成功/警告/错误提示用对应功能色，不得混用
3. **可读性基线**：正文文字对比度 ≥ 4.5:1；禁用态/占位符可辨识；颜色不是唯一信息载体（状态同时有文字/图标）
4. **一致性**：同层级元素同色阶；边框/分割线/背景使用中性色阶令牌；亮暗模式如适用则双模式检查
5. 参考 `<SKILLS_ROOT>/ui-ux-pro-max/SKILL.md` 的 Pre-Delivery Checklist 补充交互视觉项（cursor-pointer、hover 反馈不位移、过渡 150-300ms、图标不用 emoji）；`<SKILLS_ROOT>` 由主流程按标准目录探测解析，禁止从 index 文件读取

## 4. 报告格式（固定模板）

```markdown
# 自检报告 · <change-id 或主题>（第 N 轮）

## 结论总览
| 维度 | 结论 | 通过/问题数 |
|------|------|------------|
| 功能点切片 | 通过/不通过 | 12/14 |
| 交互逻辑   | 通过/不通过 | 8/9 |
| 颜色配色   | 通过/不通过 | 5/6 |

## 功能点切片对账表
| # | 切片（来源 Requirement/任务号） | 实现位置 | 状态 | 说明 |

## 问题清单
| issue_id | 维度 | 级别(blocker/major/minor) | 位置 | 问题 | 修复建议 |

## 本轮修复记录（第 2 轮起）
```

## 5. 修复闭环

1. blocker/major 必须修复；minor 可列入人工确认项（须用户可见）
2. 修复 → **复检**（只复检问题项+受影响链路）→ 仍有问题继续，**最多 3 轮**
3. 3 轮未收敛 → 停止，输出未收敛问题、原因分析、人工确认项，交用户决策；禁止无限自我修复，禁止静默放过
4. 最终报告写入 `openspec/.project-frontend/self-check/<日期-change-id>.md`，结论进入阶段 5 交付总结。A/B 续接路径不得把报告内容回写到任何 index 文件；C 现场开发路径是否回写由主流程另行决定
